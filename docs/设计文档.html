悬浮行情 App（BTC · iOS）设计文档

项目代号 FloatingTicker ｜ 版本 v1.2 ｜ 日期 2026-09-17 ｜ 主力机 iPhone 17 Pro Max ／ 测试机 iPhone 17（均 iOS 26），最低支持 iOS 17 ｜ 形态：画中画悬浮行情条

一句话定义：在 iPhone 上实现一个可悬浮于任意 App 之上的实时 BTC 行情条，采用 iOS 画中画（Picture-in-Picture, PiP）技术，全程无需 Mac 本地环境，零硬件成本完成开发与自用部署。

1. 项目概述

1.1 目标（Goals）

  • 目标设备：主力机 iPhone 17 Pro Max（最终长期使用），测试机 iPhone 17（承担全部试验性验证）。两台均运行 iOS 26；工程部署目标设为 iOS 17.0，保留向下兼容能力
  • 在任意 App 之上显示实时 BTC 价格（悬浮窗 floating overlay）
  • 价格 1Hz 级别刷新，肉眼体验为实时
  • 国内网络直连可用（无需翻墙），并能自动切换到兜底源
  • 零硬件成本：不购买 Mac，不购买 Apple 开发者付费账号

两台设备同代、同系统版本（iOS 26）、同架构（arm64），因此在测试机上验证通过的结论可直接迁移到主力机，不存在机型差异风险；两台均具备灵动岛，第二版若引入实时活动（Live Activity）也无需区分机型。

设备角色分工（重要）：所有高风险验证（侧载链路打通、PiP 可用性探测、反复失败的构建试验）一律先在测试机 iPhone 17 上做；主力机 iPhone 17 Pro Max 只在验证通过后安装稳定版本。理由有二：① 免费账号的设备注册名额有限且消耗后不易回收，主力机的名额只用于装确定可用的版本；② 试验阶段的签名失败、证书反复更换、App 崩溃等现象不干扰主力机的日常使用。

1.2 非目标（Non-Goals）

  • 不做 K 线图、盘口、下单等交易功能
  • 不做多币种（仅 BTC）
  • 不做 Android 版本
  • 第一版不做灵动岛 / 实时活动（Live Activity）
  • 不做 App Store 上架、不做多用户分发

1.3 必须接受的平台事实（Platform Constraints）

iOS 禁止第三方 App 在其他 App 之上绘制任意视图。没有 Android 那种系统级悬浮窗权限（SYSTEM_ALERT_WINDOW）。

唯一合法途径是画中画：系统托管的悬浮视频窗口，可置顶于桌面与任意 App 之上。

因此本项目本质是：把行情数据渲染成"视频帧"，用 PiP 播放。

PiP 窗口的尺寸同样不受 App 控制。系统固定了窗口的高度（小档约 96pt），宽度则等于「窗口高度 × 画面宽高比」。没有公开 API 能设定窗口尺寸，用户侧的双指捏合缩放实测亦不生效。

唯一可用的杠杆是画面宽高比：想缩小浮窗就调小比例（代价是窗口形状趋"方"），想放大就调大比例。

4.3 健康检查与切换策略（Health Monitor）

项策略
停滞判定10 秒无任何推送判定停滞（正常约每秒一条）
自愈动作停滞 → 重建当前源；连续重建 2 次无效 → 切换下一层；到底后回绕链首继续重试（永不放弃）
恢复冷却10 秒 —— 真正断网时避免高频重连（省电）
连接级心跳WebSocket 源每 15 秒发协议级 ping，把「半死连接」暴露为失败
网络恢复NWPathMonitor 检测到网络由「不可达」恢复 → 立即重建（绕过冷却）
回到前台App 回到前台（含锁屏解锁）→ 立即核对新鲜度，停滞则立即自愈
可观测性App 内显示当前数据源、推送次数、最后推送时间与完整切换日志
为什么不能只靠「失败才降级」——本条来自真机故障
现象：锁屏回来后行情不再更新。
根因：锁屏 / 后台时 iOS 会静默掐断 TCP（NAT 超时），而客户端正阻塞在 receive()， 收不到任何 error —— 连接进入「半死」状态：既不报失败，也永远收不到数据。 若降级只挂在「源主动报 failed」上，就会永久卡死。
本版把数据停滞看门狗设为总指挥：它不关心失效原因（半死连接、服务器无推送、切换网络丢连接）， 只要「没有数据」就一路 重建 → 降级 → 回绕，直到恢复。协议级心跳用于尽早把半死连接暴露出来，加速恢复。

选型注意：L1 与 L2 同域，同域封禁时会同时失效，因此 L3 必须是异构（不同厂商、不同 CDN）的源才具兜底价值。

4.6 源优先级自适应（Adaptive Source Priority，2026-09-21）

需求：用户希望「能用欧易（OKX）就用欧易，不能用就走 Gate / CoinEx」。而 OKX 仅代理环境可达（直连被 TLS 阻断、www.okx.com 遭 DNS 污染），因此需要一个判断依据。

为什么不用「检测是否开了 VPN」

检测手段结论
CFNetworkCopySystemProxySettings()只覆盖 HTTP/HTTPS/SOCKS 代理设置；TUN 模式 VPN（Shadowrocket / Surge / Clash 默认）不写这些键，读不到
NEVPNManager 连接状态只能读本 App 自己创建的 VPN 配置，跨 App 无效；且需要 NetworkExtension 权限
枚举网络接口找 utun* / ppp*会误判：系统自身的 iCloud 私密代理、Wi-Fi Calling 同样创建 utun 接口（已有公开 issue 证实此类 false positive）
语义层面状态 ≠ 能力：挂了代理但分流规则把目标域名走直连，照样不通；反之某些运营商 / 内网环境能直连却没有 VPN 标志
决策：改为 可达性探测（reachability probe） —— 直接验证目标端点此刻是否可达。 判断依据是事实而非推断，结论在任何网络形态（VPN / 分流规则 / 内网代理 / 运营商差异）下都成立。

探测实现（Sources/Market/SourceProbe.swift）

项取值理由
探针端点GET https://www.okx.com/api/v5/public/time无参数、响应体最小；不用行情接口是为了避开频控（rate limit）
超时3 秒代理链路首次 TLS 握手偏慢（实测 OKX REST 经代理约 1.5s），但超过 3 秒才响应的话，作为实时行情源已无意义
判定规则无错误 + HTTP 200 + 业务码 "0"三者缺一不可：被劫持时常见「HTTP 200 但响应体不是预期结构」，只看状态码会误判
触发时机仅 TickerStore.start() 执行一次成本极低（几 KB）；「当前网络能否通 OKX」在一次会话内基本稳定

启动时序（探测不阻塞首帧）

start()
 ├─ 立即启用 Gate 链（Gate WS → Gate REST → CoinEx REST）
 │     └─ 首帧行情秒级到达，用户无感
 ├─ 后台探测 OKX（3s 超时）
 │     ├─ 可达   → 把 OKX 插到链首并立即切换 → 优先使用 OKX 永续 WS
 │     └─ 不可达 → 保持 Gate 链（日志记录判定依据与耗时）
 └─ 心跳看门狗启动（5s 粒度，仅记日志）

优先级链（failover chain）

探测结果链序（自左向右依次降级）
可达（通常已挂代理）OKX 永续 WS → Gate 永续 WS → Gate 永续 REST → CoinEx 永续 REST
不可达（直连环境）Gate 永续 WS → Gate 永续 REST → CoinEx 永续 REST（＝原链）

注意：OKX 之后仍保留 Gate，即「欧易挂了立刻回 Gate」，而不是直接掉到异构兜底源。

连带处理的三件事（否则会引入新 bug）

  1. 跨源基差跳变（basis jump）：不同交易所有基差（实测 CoinEx 77879 / Gate 77935 / OKX 77947，约 0.09%），切换源瞬间价格会跳变。而报警用的是穿越判定（比较上一价与当前价），若把这笔跳变当作真实行情，会凭空触发一次误报。处理：TickerStore.onSourceChanged 回调通知 AlertEngine，切源后的首笔快照仅作为基准价，不参与穿越判定。
  2. OKX 保活（keep-alive ping）：OKX 对空闲连接有超时要求，客户端需定时发 ping，否则会被服务端断开 —— 表现是「连上约半分钟后莫名降级」，属假故障，最易踩坑。处理：OKXFuturesWebSocketSource 内 20 秒定时 ping（留足余量）。
  3. 过期探测结果：探测是异步的，期间源链若被重建（重新 start / stop），迟到的结果会把已停用的源又启起来。处理：probeGeneration 代次校验，过期结果直接丢弃。

已知边界（Known Limitation）：探测只在启动时执行一次。会话中途开关 VPN 不会重排优先级，需重启 App 才生效；若需实时响应网络变化，可接入 NWPathMonitor 监听路径变化后重探（属后续可选增强，本轮未做）。

5. PiP 渲染管线

MarketStore（行情状态聚合）
      ↓ 价格变化通知
FramePump（帧泵，自适应帧率）
      · 价格变化 → 立即出帧
      · 静止状态 → 1 fps 心跳保活（keep-alive）
      ↓
TickerFrameRenderer（CoreGraphics 绘制 → CVPixelBuffer）
      · 币对名 · 最新价（等宽数字，避免宽度抖动）
      · 涨跌幅标签（绿涨红跌）
      ↓
SampleBufferFactory（CVPixelBuffer → CMSampleBuffer）
      ↓
AVSampleBufferDisplayLayer
      ↓
AVPictureInPictureController → 系统悬浮窗

5.1 关键实现点

要点做法原因
会话保活AVAudioSession 设为 .playback 并 setActive(true)PiP 会话在后台存活、持续刷新价格的前提
内容源ContentSource(sampleBufferDisplayLayer:playbackDelegate:)iOS 15+ 的自定义帧源接口
伪装直播流时间轴返回 .positiveInfinity隐藏进度条，只保留播放/关闭控件
画面比例由画布（CVPixelBuffer）尺寸决定，现取 640×400（1.6:1）比例是唯一能调整窗口大小的杠杆（见下一行）
窗口尺寸无法直接设定。系统规则为：窗口高度固定（小档约 96pt），宽度 = 高度 × 画面宽高比。故做法是加高画布、内容垂直居中、上下留底色，让窗口整体缩小无公开 API 可设置 PiP 窗口尺寸，真机实测捏合缩放不生效。实测数据：640×200（3.2:1）→ 窗口 307×96；640×400（1.6:1）→ 窗口 154×96（面积减半）。附带收益：系统控件（关闭、画中画图标）压在窗口四角，留白后不再遮挡币对名
回到 App实现 restoreUserInterfaceForPictureInPictureStop用户点击"还原"时正确切回前台
数字防抖使用等宽数字（monospaced digits）价格跳动时不产生布局抖动
省电价格未变化时降到 1 fps帧泵是持续耗电点
后台模式Info.plist 声明 UIBackgroundModes: audioPiP 会话后台存活
像素缓冲必须由 IOSurface 支撑（kCVPixelBufferIOSurfacePropertiesKey）图层走硬件合成管线；缺少该属性时帧能入队、状态显示 .rendering，却永远全黑——本项目实测踩过此坑（第 13 章）
时间基显式创建并设置 controlTimebase，帧 PTS 取该时间基的当前时间图层默认没有时间基（实测为 nil），帧无法判定显示时刻。创建接口为 CMTimebaseCreateWithSourceClock(allocator:sourceClock:timebaseOut:)（输出参数 + OSStatus 返回）
宿主容器容器视图保持 1×1，显示层尺寸用画面尺寸实测换成可见大容器后 startPictureInPicture() 会静默失败（无任何回调）
立即显示样本缓冲带 kCMSampleAttachmentKey_DisplayImmediately直播式内容需强制立即出画，不等时间戳
播放控制sample buffer 模式下系统会禁用快进/快退控制与"伪直播流"设计方向一致，无需额外处理；目标系统 iOS 26 下该组合仍为 Apple 官方支持的内容源

13. 功能：价格报警（Price Alert）

当 BTC 价格到达设定目标（默认 69000）附近时，同时给出声音警报与悬浮窗视觉警报。

13.1 触发状态机（迟滞设计）

ARMED（已武装）
   │ 价格由带外触及 / 穿越触发带 [目标−容差, 目标+容差]
   ↓
ALERTING（报警中）   声音 + 震动 + 红闪，持续到用户按「停止」为止（无自动停止）
   ↓ 用户按「停止」
COOLDOWN（冷却）     默认 1 分钟内不再触发（界面可改），从"停止那一刻"起算
   ↓ 冷却到 && 价格已离开解除带（±容差×2）
   └→ 回到 ARMED

为什么必须做迟滞：若只用"进入容差带即报警"，价格在阈值附近徘徊时会每几秒报一次，实际上等于不可用。故要求价格先真正离开（默认 ±100），才允许下一次触发。

停止入口共三处 —— 报警很可能在你的手机躺在兜里、你在刷别的 App 时触发，所以必须让它随处可停：
① 浮窗的暂停键：在别的 App 里唯一能碰到的控件，故把系统的"暂停"直接当作"停止"用；
② App 顶部的红色停止按钮：点浮窗回到 App 后，第一眼（列表最顶部）就能按到；
③ 设置卡片里的「停止报警」：兜底入口。
另外，直接关掉浮窗也会连带停止（App 被挂起后本就无法继续响）。

触发判定覆盖"跳穿"：判据是「上一价在带外 && 当前价已进入或越过上沿」。因此价格从 69200 直接跳到 68800（中间没有任何一帧落在带内）同样能触发，不会漏报。

13.2 报警音：代码合成，不用音频素材

项做法原因
音色2200Hz 方波「嘀-嘀-嘀」：每声 0.10s、间隔 0.07s、三连后静默 0.55s，整段约 1.06s 并循环方波谐波丰富、穿透力强，比正弦波更容易在嘈杂环境被听见 —— 这是"辨识度高"的关键
实现运行时合成 16bit PCM，手工拼 44 字节 WAV 头，交给 AVAudioPlayer（numberOfLoops = -1）仓库由 CI 构建，不宜携带二进制音频素材；合成音完全可控，能与任何手机自带通知音区分开
静音开关不受影响（音频会话为 .playback）该类别下音频无视静音开关 —— 这是 PiP 保活所用会话白捡的好处
会话抢占出声前显式 setActive(true) 抢回会话；并监听打断事件，报警中被抢后自动抢回并重新出声"刷着抖音还能不能报警"的关键：我们平时不发声，用户切去刷抖音时系统会把会话让给对方、我们的会话被 deactivate —— 此时直接 play() 会没有声音且无任何报错
音量App 侧输出拉满，实际响度取决于「媒体音量」iOS 不允许 App 强制修改系统音量
震动节奏与警报音对齐：0.17 秒一拍的连震三下 + 静默，循环往复（起手另加一次系统级强震）前台可靠生效；**后台/锁屏时 iOS 基本不允许 App 主动震动**，属尽力而为（见 13.4）。要求后台必定震动只能靠本地通知，但那样必然弹横幅并带系统提示音

13.3 悬浮窗视觉警报

  • 价格数字：报警红 #ff4545 ↔ 纯白，以 2 Hz 交替闪烁
  • 整窗红光脉冲：两级透明度交替，形成"呼吸"感而非硬闪
  • 四边红框：画布 640 宽映射到窗口约 154pt，14 单位 ≈ 3.4pt
  • 左上角标题：报警期间临时替换为「⚠ 69000 已触及」，一行说清发生了什么
  • 帧率：常态 1 fps → 报警期间 4 fps（1 fps 下文字根本闪不起来；4 fps 恰好每相位 1 帧，既干净又比 8 fps 省一半——报警现在不会自动停止，可能持续很久）
闪烁频率刻意压在 3 Hz 以下：3~30 Hz 的闪烁对光敏性癫痫人群存在风险。取 2 Hz（半周期 0.25 秒）——同样醒目，但避开风险区间；配合报警期间 8 fps，恰好每相位 2 帧，交替干净不抖动。

13.4 限制（平台硬边界）

限制说明
浮窗必须存活报警依赖 PiP 会话在后台运行。用户手动关闭浮窗后不会有任何报警 —— 这是 iOS 的硬边界，无法绕过
报警会打断其他 App 的音频抢回会话是抢占式的，抖音/音乐会被暂停。对报警而言这是期望行为（确保一定能被听见）；若要"叠在对方声音上响"，把类别选项改为 mixWithOthers 即可（可听度会下降）
音量取决于媒体音量不是铃声音量。媒体音量调到 0 就真的没有声音
无法穿透专注模式"关键警报"权限需付费账号 + Apple 审批，免费账号不具备
后台震动基本不可用iOS 不允许后台 App 主动振动（UIFeedbackGenerator 在后台是空操作）。前台可靠、后台尽力而为，故辨识度主力仍是声音与闪烁。若必须后台也震：唯一可靠途径是发本地通知（系统通知按用户设置震动），代价是必然弹横幅 + 带系统提示音，iOS 不提供"只震不响"的通知

13.5 可配置项（持久化到 UserDefaults）

配置默认值说明
目标价69000触发基准，可在界面直接修改
容差±50把"到达附近"量化成价格带，避免用浮点相等判定
方向仅向下跌破可切换为双向（涨到或跌到都报）
报警时长无（持续到手动停止）按用户要求：不按「停止」就一直响；试听例外，固定 6 秒自动停
冷却1 分钟与迟滞配合，防止反复轰炸；可在界面直接改
「试听报警」按钮是必需品，不是装饰：目标价通常离现价很远（现价约 76300、目标 69000，相差 9.6%），没有它就无法验证报警链路是否正常。试听时长 6 秒，不进冷却、不污染实盘状态。
由于目标价可编辑，把目标价改成现价附近（容差 ±50）即可在几秒内验证真实的触发链路。
参数变更即重置状态机：改目标价 / 容差 / 方向后立刻回到「已武装」，并清空冷却与上一价。既避免"改完参数还得等 5 分钟冷却"的困扰，也让"改成现价附近即触发"这种验证方式成立。

            ↓
   xcrun altool --upload-app → TestFlight
设计点做法原因
安全跳过凭据检查的结论经 step output 传递给后续步骤的 ifGitHub Actions 的 if 无法直接引用 secrets；这样可在密钥就绪前先合并本文件，且不把 CI 弄红
签名App Store Connect API 密钥 + -allowProvisioningUpdates证书与描述文件由 Xcode 自动创建/下载，无需手工维护 .p12 与 profile，是 CI 场景下最省心的方式
构建号CURRENT_PROJECT_VERSION 取 GITHUB_RUN_NUMBER同一版本号重复上传会被 App Store Connect 直接拒收，这是 CI 自动上传最经典的坑
导出方式按 Xcode 主版本自动选择 app-store-connect / app-store该取值在 Xcode 15 变更过，硬编码会在换 runner 镜像时失败
plist 生成plutil -create xml1 + PlistBuddy避免 heredoc 把 XML 声明缩进坏掉导致 plist 非法
密钥落盘以 base64 存 Secrets，用 openssl base64 -d -A 解码到 ~/.appstoreconnect/private_keys/Secrets 不适合存多行文本；openssl 在 macOS/Linux 参数一致

15.3 三个关键坑（2026-09-21 实测踩坑记录）

坑一：401 认证失败 = 三件套「配对」错位，而非格式错误
现象：archive 阶段 listTeams.action 返回 401，连带报 No profiles ... were found。
定位：加「密钥自检」步骤——openssl ec 解析私钥、核对 Key ID / Issuer ID 长度、构造 JWT 直连 api.appstoreconnect.apple.com 看返回码。
根因：Key ID / Issuer ID / p8 三者不是同一把钥匙的三个零件（从旧账号 / 旧 key 串了值）。
解法：三值必须同源——Issuer ID 取「用户和访问 → 集成 → App Store Connect API」页面顶部；Key ID 与 p8 必须来自同一把 key（新建的那把）。
坑二：Cloud signing permission error = 密钥缺「云托管分发证书」权限
现象：archive 成功，但 exportArchive 报 Cloud signing permission error，进而 No profiles。
根因：cloud signing 需要密钥具备「Access to Cloud Managed Distribution Certificate」权限；App Manager 角色并不够。且 App Store Connect 页面明示「Keys don't expire, but can't be modified to access more services once created」——密钥创建后权限不可改。
解法：吊销重建，Access 选 Admin（Admin 自带该权限），重新下载 p8、更新 Secrets（Issuer ID 不变）。
坑三：构建全绿但安装链接 404 = GitHub Pages 未启用
现象：workflow 全部 success（含 Publish to GitHub Pages），但访问 manifest.plist / .ipa 都是 404。
根因：peaceiris/actions-gh-pages 只是把文件推到 gh-pages 分支，仓库未启用 Pages 就不会部署站点。
解法：仓库 Settings → Pages → Source 选「Deploy from a branch」→ Branch 选 gh-pages / (root) → Save，约 1~2 分钟生效。

  1. 手机 Safari 打开 itms-services://?action=download-manifest&url=https://<owner>.github.io/<repo>/manifest.plist（本项目为 suzilujie.github.io/floating-ticker/manifest.plist）
  2. 点「安装」→ 桌面出现图标
  3. 首次打开被拦：设置 → 通用 → VPN 与设备管理 → 信任开发者证书
